# 架构主线

## 如何思考架构

当你要组织代码结构时，问自己：

**"一个新人从入口出发，能否顺着代码追踪到完整的业务流程？需要跳几个文件？"**

如果超过 3 个文件，说明太分散了。如果中间有隐式传递（事件总线、魔法字符串、全局变量），说明链条断了。

## 统一链条

所有业务流程走同一条路径：

**触发 → 指令 → 数据 → 反馈**

为什么是这条链条？因为它符合人脑对"做一件事"的直觉理解：某件事发生了 → 执行一个动作 → 数据变了 → 看到结果。

### 触发入口

入口只做一件事：接收事件，调用对应指令。

问自己："入口里有没有在做业务计算？" 如果有，把业务搬到指令里去。入口只是一个路由器。

### 指令执行

指令只做业务动作：读数据、处理、改数据、返回结果。

问自己："这个指令里有没有在操作 UI、发送响应、做渲染？" 如果有，那它在做不属于它的事。指令只管数据。

按业务主体组织：`commands/task.js` 包含 `add`、`remove`、`toggle`、`rename`。一个主体的全部操作在一个文件里找到。

### 数据存储

数据集中存放，结构一目了然。

问自己："想知道某个数据长什么样，需要去几个地方找？" 如果超过一个地方，说明数据分散了。

### 通用工具

问自己："这个函数只有当前业务在用，还是多个业务都在用？拿到别的项目还能用吗？"

只有两个都回答"是"才放进工具目录。否则就地写在业务代码里。

## 零注册

当你要新增一个模块时，问自己：

**"写完这个文件后，我还需要去其他地方注册它吗？"**

如果需要，架构设计有问题。正确做法：
- 约定目录结构（`commands/`、`tools/`、`plugins/`）
- 约定统一导出格式
- 启动时自动扫描目录注册

新增 = 写好放进去。删除 = 把文件删掉。不碰其他任何文件。

## 项目结构

问自己："这个目录里文件够多吗？值得单独建文件夹吗？"

| 文件数量 | 做法 |
|----------|------|
| 少于 4 个 | 平铺在目录下 |
| 4–8 个 | 按业务分 1 层文件夹 |
| 超过 8 个 | 按业务分 2 层文件夹 |

不为一两个文件建文件夹。能一个文件搞定的事就一个文件搞定。

## 拆分判断

想要拆文件时，问自己：

**"这个文件是因为太大了不好读才拆，还是为了'架构正确'才拆？"**

如果业务本身就简单，一个文件 100 行就能写完所有逻辑，那就不拆。拆了反而让人要跳来跳去。

只有当一个文件里的不同部分变动频率明显不同，或者真的大到读不动了，才拆。
