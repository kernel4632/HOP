# 架构主线

## 唯一链条

一切业务流程按统一链条组织：

**触发 → 指令 → 数据 → 反馈**

这条链条让任何人从入口出发，顺着追踪就能理解完整流程，不超过 3 跳。

## 各层职责

### 触发入口

- 只负责接收事件、判断谁触发了什么、调用对应指令
- 不处理业务逻辑，不做数据计算，不直接修改数据
- 可以是 UI 事件处理、HTTP 路由、CLI 解析器、消息监听器等

### 指令执行

- 只负责完成一次清晰的业务动作：读数据、处理、改数据、返回结果
- 指令不操作 UI，不发送响应，不做渲染
- 按业务主体命名文件，该主体的全部操作集中在一起：`commands/task.js` 包含 `add`、`remove`、`toggle`、`rename`
- 指令之间通过组合调用实现复杂功能，不嵌套不继承

### 数据存储

- 集中存放在 store / data 中，结构显式可见
- 数据文件只定义和暴露数据结构，不包含业务逻辑
- 数据变化自动驱动反馈（响应式机制由框架提供）

### 通用工具

- 仅放多主体复用、可移植到其他项目的纯函数
- 只有多个主体都在用、拿到别的项目也能用的函数才允许放进去
- 工具函数不含业务身份，不操作 store，不调用指令

## 零注册

新增模块按约定格式写好，放到对应目录，启动时自动扫描生效。删除模块把文件删掉就消失。

实现方式：
- 约定目录结构（`commands/`、`tools/`、`plugins/`）
- 约定统一导出格式
- 启动时自动扫描目录并注册
- 不维护手动注册清单，不硬编码 import 列表

判断标准：新增或删除一个功能模块后，如果需要修改该模块之外的任何文件，说明违反了零注册原则。

## 项目结构

| 文件数量 | 组织方式 |
|----------|----------|
| 少于 4 个 | 直接平铺在目录下 |
| 4–8 个 | 按业务分 1 层文件夹 |
| 超过 8 个 | 按业务分 2 层文件夹 |

每个文件夹至少含 4 个文件，否则不建文件夹。能一个文件搞定的事就一个文件搞定。

## 减法原则在架构中的体现

- 不为"解耦"把一个文件能搞定的事拆成多个文件
- 不为"可能复用"提前创建抽象层
- 不为"职责分离"创建只用一次的辅助文件
- 业务简单，代码就必须简单。项目的复杂度和业务复杂度保持 1:1

## 追踪验证

任何人看到入口的一个调用，都能顺着链条完成追踪：

1. 入口文件 → 调用了哪个指令
2. 指令文件 → 读了哪些数据、改了哪些数据
3. 数据文件 → 完整数据结构，知道改动影响了什么
4. 反馈自动发生

如果追踪过程需要跳转超过 3 个文件，或中间有隐式传递（事件总线、魔法字符串、全局变量），说明架构偏离了主线。改架构，不加保护代码。
