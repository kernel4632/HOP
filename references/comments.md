# 注释准则

## 核心定位

注释让不懂代码的人也能读懂每一步在做什么。说业务含义，不复述语法。

## 密度要求

- 每一行承载业务含义的代码都配备注释
- 一个函数内不应存在连续超过 2 行的无注释代码
- 每条注释必须回答以下至少一个问题：
  - 这步在做什么业务动作？
  - 为什么这么做？
  - 数据从哪来、会变成什么、会影响哪里？

## 禁止的废话注释

只复述语法、不提供信息增量的注释禁止出现：

```
count = 0           // 将count设为0           ← 废话
arr.push(item)      // 将item推入数组         ← 废话
return result       // 返回结果               ← 废话
```

正确做法——说业务含义：

```
count = 0           // 计数器归零，准备重新统计未读消息
arr.push(item)      // 将新任务加入待处理队列
return result       // 返回过滤后的有效订单列表
```

## 格式规则

### 文件头注释

用多行注释，大白话说清楚：这个文件做什么、怎么调用。

```js
/*
任务指令集：负责任务的增删改查。
数据存储在 store.tasks 数组中，每个任务含 id、title、done 三个字段。
调用示例：Task.add("完成报告")、Task.remove("task_01")、Task.toggle("task_01")
*/
```

不使用 `@module`、`@description`、`@author`、`@param`、`@returns` 等标注格式。

### 段落标题

每个函数或逻辑段前使用段落标题作为视觉分隔：

```js
// --- 添加任务 ---
```

标题描述该段要完成的动作，不是复述函数名。

### 尾随注释

写在代码行末尾，同一代码块内对齐到统一列位置，形成"左侧代码、右侧注释"的双栏阅读：

```js
const taskId = generateId()                    // 生成唯一任务ID
const newTask = { id: taskId, title, done: false }  // 构建新任务对象
store.tasks.push(newTask)                      // 将任务加入全局列表
```

连续单行操作紧凑排列、每行配备尾随注释，不留空行。

### 行注释

当一行注释对应多行代码块时，写在代码块上方。

### 必须注释的位置

- import / require 语句：说明引入的是什么能力
- export 语句：说明导出了什么
- 模块级变量：说明用途
- 卫语句：说明为什么提前返回

## 必须注释的场景

- 魔法数字：为什么是这个值
- 特殊顺序：为什么这个操作在前
- 不符合直觉的写法：为什么不用更常见的方式
- 改了会影响别处的代码：影响哪里
- 设计决策的取舍：为什么选 A 不选 B

把写代码时的思考写进注释。代码会遗忘背景，注释保留决策上下文。
