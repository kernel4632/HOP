# 注释准则

## 如何思考注释

写完一段代码后，问自己：

**"一个完全不懂这个项目、甚至不太懂编程的人，能读懂这段代码每一步在做什么业务吗？"**

如果不能，加注释。注释说的是"这一步在做什么业务动作"，不是"这行语法是什么意思"。

## 判断注释是否有信息量

写完注释后，问自己：

**"把代码删掉只留注释，读者能知道这步在做什么吗？"**

能 → 好注释。不能 → 废话注释，重写。

废话注释：
```
count = 0           // 将 count 设为 0
arr.push(item)      // 将 item 推入数组
return result       // 返回结果
```

有信息量的注释：
```
count = 0           // 计数器归零，准备重新统计未读消息
arr.push(item)      // 将新任务加入待处理队列
return result       // 返回过滤后的有效订单列表
```

区别：前者在复述语法，后者在说业务含义。

## 密度

问自己："这个函数里有没有连续超过 2 行的代码没有注释？"

如果有，说明那几行的业务含义没有被说清楚。每一行承载业务含义的代码都值得一条注释。

## 格式

### 文件头

打开文件第一眼看到的东西。用大白话说：这个文件做什么、怎么调用。

```js
/*
任务指令集：负责任务的增删改查。
数据存储在 store.tasks 数组中，每个任务含 id、title、done 三个字段。
调用示例：Task.add("完成报告")、Task.remove("task_01")
*/
```

不用 `@module`、`@param`、`@returns` 这些标注格式。大白话比标注格式更容易读。

### 段落标题

每个函数前面用段落标题做视觉分隔：

```js
// --- 添加任务 ---
```

标题说这段要完成的动作。读者扫一眼就知道每段在做什么。

### 尾随注释

写在代码行末尾，同一块内对齐到统一列位置：

```js
const taskId = generateId()                    // 生成唯一任务ID
store.tasks.push(newTask)                      // 将任务加入全局列表
return taskId                                  // 返回新任务ID供调用方使用
```

连续操作紧凑排列，每行一条注释，形成"左代码右解说"的双栏节奏。

### 必须注释的位置

- import 语句：引入的是什么能力
- export 语句：导出了什么
- 模块级变量：用途是什么
- 卫语句：为什么提前返回

### 必须注释的场景

问自己："如果不写注释，下一个看这段代码的人会困惑吗？"

以下情况一定会困惑，所以一定要写：
- 魔法数字——为什么是这个值
- 特殊顺序——为什么这个操作在前面
- 不直觉的写法——为什么不用更常见的方式
- 会影响别处——影响了哪里
- 取舍决策——为什么选 A 不选 B

把写代码时脑子里的思考写进注释。代码会遗忘背景，注释保留决策上下文。
