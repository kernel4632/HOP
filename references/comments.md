# 注释格式

## 注释的目的

注释让一个完全不懂这个项目、甚至不太懂编程的人，也能读懂每一步代码在做什么业务。

判断一条注释好不好，有一个简单的办法：把代码删掉只留注释，读者还能知道这步在做什么，那就是好注释。如果只剩注释就不知道在干什么，那是废话注释，要重写。

废话注释只是在复述语法：

```js
count = 0           // 将 count 设为 0
arr.push(item)      // 将 item 推入数组
return result       // 返回结果
```

有信息量的注释说的是业务含义：

```js
count = 0           // 计数器归零，准备重新统计未读消息
arr.push(item)      // 将新任务加入待处理队列
return result       // 返回过滤后的有效订单列表
```

## 密度

每一行承载业务含义的代码都值得一条注释。如果一个函数里出现连续好几行没有注释的代码，说明那几行的业务含义没有被说清楚。

## 修改已有代码也要注释

修改已有代码时，同样要给被修改的那几行补上注释。不要只在新写的代码上加注释，修改的地方反而没有。人看到一段被改过的代码，需要知道这一行在做什么、这一段在执行什么流程，这些都要靠注释说清楚。

## 文件头注释

文件开头用大白话说清楚这个文件做什么、怎么调用，不用 `@module`、`@param`、`@returns` 这类标注格式：

```js
/*
任务指令集：负责任务的增删改查。
数据存储在 store.tasks 数组中，每个任务含 id、title、done 三个字段。
调用示例：Task.add("完成报告")、Task.remove("task_01")
*/
```

## 段落标题

每个函数前面用段落标题做视觉分隔，标题说这段要完成的动作：

```js
// --- 添加任务 ---
```

## 尾随注释

写在代码行末尾，同一块内对齐到统一列位置，形成"左边代码、右边解说"的双栏节奏：

```js
const taskId = generateId()                    // 生成唯一任务ID
store.tasks.push(newTask)                      // 将任务加入全局列表
return taskId                                  // 返回新任务ID供调用方使用
```

## 必须注释的位置

import 语句要说明引入的是什么能力，export 语句要说明导出了什么，模块级变量要说明用途，卫语句要说明为什么提前返回。

## 必须注释的场景

遇到这些情况一定要写注释：魔法数字为什么是这个值，操作顺序为什么这样安排，不符合直觉的写法为什么不用更常见的方式，改了会影响别处的代码影响了哪里，设计决策为什么选 A 不选 B。

把写代码时脑子里的思考写进注释。代码会遗忘背景，注释保留决策的上下文。
